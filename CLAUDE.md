# Quiz-платформа

Платформа квизов с игрой в реальном времени: FastAPI + PostgreSQL 18 + Centrifugo v6 + React 19.

- **Что строим:** `docs/SPEC.md`. Это источник истины.
- **Отклонения от ТЗ:** только с записью в `docs/decisions.md` и причиной.
- **Этапы:** `tasks/BACKLOG.md`, описание каждого в `tasks/TASK-XXX-*.md`.

## Окружение: только Docker

Всё запускается через `docker-compose`. На хосте не запускай `python`, `pip`, `uv`, `pytest`, `ruff`, `mypy`, `alembic`, `uvicorn`, `node`, `npm` и `npx` и не устанавливай пакеты. Переменные окружения берутся только из `.env` (пример лежит в `.env.example`), переменные хоста не используются.

```bash
docker-compose up --build                                   # весь стек
docker-compose run --rm backend pytest                      # тесты бэкенда
docker-compose run --rm backend pytest path::test -x        # один тест
docker-compose run --rm backend ruff check .
docker-compose run --rm backend ruff format --check .
docker-compose run --rm backend mypy app
docker-compose run --rm backend alembic upgrade head
docker-compose run --rm backend alembic revision --autogenerate -m "..."
docker-compose run --rm frontend npm test                   # Vitest
docker-compose run --rm frontend npm run lint
docker-compose run --rm frontend npm run typecheck
docker-compose run --rm frontend npm run generate:api       # типы из OpenAPI
docker-compose build <service>                              # после изменения зависимостей
```

Порты: фронт 5173, бэкенд 8080, Centrifugo 8000, PostgreSQL 5432, Redis 6379.

## TDD: обязательный цикл

Код пишется только для того, чтобы прошёл уже написанный падающий тест.

1. **Red.** По одному критерию приёмки напиши тест, запусти его и убедись, что он падает по ожидаемой причине: из-за отсутствующего поведения, а не из-за опечатки или импорта. Вывод падения покажи в отчёте.
2. **Green.** Напиши минимальный код, чтобы тест прошёл. Запусти этот тест и затем весь набор.
3. **Refactor.** Улучши код при зелёных тестах. После каждого изменения снова запускай тесты.
4. Повтори для следующего критерия.

Правила:

- Сначала тесты для чистой логики (`game/checker.py`, `game/scoring.py`, нормализация slug), затем для сервисов, затем HTTP и realtime.
- Если баг найден, сначала напиши тест, который его воспроизводит, и только потом исправляй.
- Нельзя менять тест одновременно с кодом, который он проверяет, чтобы тест прошёл. Если тест неверен, остановись и объясни почему.
- Не ослабляй и не удаляй тесты. Не используй `skip`, `xfail`, `# type: ignore`, `# noqa` и `eslint-disable` без согласования.
- Тест проверяет поведение через публичный интерфейс (HTTP API, функцию модуля, компонент), а не внутреннюю реализацию. Моки допустимы только для внешних границ: часов, Centrifugo server API, сети.
- Время в тестах контролируется. Таймеры раундов и дедлайны проверяются через подменяемые часы, а не через `sleep`.

## Где какие тесты

| Что | Чем | Где |
|---|---|---|
| Чистая логика (checker, scoring, slug) | pytest, без базы | `backend/tests/unit/` |
| Сервисы, репозитории, API | pytest + `httpx.AsyncClient` + PostgreSQL из compose (база `quiz_test`) | `backend/tests/integration/` |
| Гонки (два ответа, закрытие раунда) | pytest, параллельные сессии к настоящей базе | `backend/tests/integration/` |
| Публикация событий | pytest, Centrifugo server API подменён записывающим клиентом | `backend/tests/integration/` |
| Компоненты и хуки | Vitest + Testing Library | `frontend/src/**/*.test.tsx` |
| Сквозные сценарии | Playwright против поднятого compose | `frontend/e2e/` |

## Порядок работы над этапом

1. Работай только над этапом, который указал пользователь. Прочитай его файл и связанные разделы `docs/SPEC.md`.
2. Покажи план: список тестов в порядке написания, затем файлы, которые изменишь. Дождись подтверждения.
3. Пройди цикл TDD по каждому критерию.
4. Выполни все проверки из раздела «Критерии готовности».
5. В отчёте перечисли:
   - какие критерии закрыты и каким тестом;
   - вывод red для каждого нового теста и итоговый вывод проверок;
   - отклонения от ТЗ (они же записаны в `docs/decisions.md`) и открытые вопросы.

## Когда остановиться и спросить

- ТЗ противоречиво или не покрывает случай. Не придумывай поведение сам.
- Нужна библиотека или решение, которого нет в ТЗ.
- Нужно изменить уже применённую миграцию, публичный API или событие предыдущего этапа.
- Проверка падает по причине вне текущего этапа.

## Правила кода

- Код и комментарии пишем на английском, документацию на русском.
- Бэкенд: модульный монолит, `router → service → repository` (`docs/SPEC.md`, разделы 4 и 9). Модули не обращаются к репозиториям друг друга, только к сервисам.
- Верные ответы никогда не попадают в публичные схемы и события до `round.ended`. Если сомневаешься, заведи отдельную схему и тест на отсутствие полей.
- Время ответа, проверку и очки считает только сервер.
- Схема БД меняется только миграциями Alembic.
- Публикация в Centrifugo выполняется после коммита транзакции.
- Кэш устроен по `docs/cache.md`: cache-aside, инвалидация после коммита, ключи только из `cache_keys.py`. PostgreSQL остаётся источником истины, а система должна работать с пустым или недоступным Redis. Публичное и приватное хранится в разных ключах.
- Версии библиотек, образов и ключи конфигурации Centrifugo сверяй с документацией, а не с памятью.
- Не делай `git commit`, `git push` и не меняй историю без прямой команды.

## Критерии готовности этапа

- Все критерии приёмки закрыты, на каждый есть тест, и для каждого нового теста показан red.
- Все команды проходят с кодом 0: `pytest`, `ruff check`, `ruff format --check`, `mypy app`, `npm test`, `npm run lint`, `npm run typecheck`.
- `docker-compose up --build` на чистых томах поднимает стек, миграции применяются.
- Покрытие модулей `game`, `questions` и `rooms` не ниже 80%, начиная с этапа, где они появились.
- Если поведение изменилось, обновлены `docs/SPEC.md` или `docs/decisions.md`. Статус этапа обновлён в `tasks/BACKLOG.md`.
