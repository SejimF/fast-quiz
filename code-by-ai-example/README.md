# Разработка с помощью ИИ: что описать агенту

Это пример комплекта документов для проекта, который пишет агент, а человек только даёт команды и проверяет результат. Для примера взят Quiz API на FastAPI, но структура подойдёт и для других проектов: достаточно заменить содержимое.

## Главная идея

Агент не знает того, что не записано, и восполняет пробелы догадками. Поэтому качество результата зависит в основном от двух вещей:

1. **Насколько однозначно описано, что нужно сделать.** За это отвечают спецификация и задачи.
2. **Может ли агент сам проверить, что получилось.** За это отвечают тесты, линтер и типы.

Если есть обе вещи, вы проверяете готовый результат, а не исправляете код за агентом после каждого шага.

## Что и где описано

| Файл | Что описывает | Что будет, если его нет |
|---|---|---|
| [`docs/SPEC.md`](docs/SPEC.md) | Что строим и зачем: сценарии, API, бизнес-правила, что не входит в проект | Агент сам придумает поведение и добавит лишние функции |
| [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) | Как строим: стек, слои, модель данных, решения и их причины | Каждая задача будет написана в своём стиле, появятся случайные зависимости |
| [`CLAUDE.md`](CLAUDE.md) | Правила работы: команды, запреты, критерии готовности. Агент загружает его в начале каждой сессии | Придётся повторять одно и то же в каждом запросе |
| [`tasks/BACKLOG.md`](tasks/BACKLOG.md) | Порядок задач и их статус | Агент возьмётся за всё сразу, и получится большой diff, который трудно проверить |
| [`tasks/TASK-004-create-quiz.md`](tasks/TASK-004-create-quiz.md) | Заполненный пример задачи с проверяемыми критериями | Непонятно, когда задача считается готовой |
| [`tasks/_TEMPLATE.md`](tasks/_TEMPLATE.md) | Пустой шаблон задачи | — |
| [`PROMPTS.md`](PROMPTS.md) | Готовые команды для каждого этапа цикла | — |
| [`.claude/settings.json`](.claude/settings.json) | Что агенту можно делать без подтверждения, а что нельзя | Придётся либо подтверждать каждую команду, либо дать лишний доступ |

## Полный цикл

```text
1. Идея          → агент задаёт вопросы, вы отвечаете        → SPEC.md
2. Проектирование → агент предлагает, вы выбираете            → ARCHITECTURE.md
3. Нарезка задач → агент дробит спецификацию, вы проверяете  → BACKLOG.md
4. Реализация    → по одной задаче: план → код → тесты       → diff
5. Ревью         → новая сессия ищет ошибки в diff           → замечания
6. Ваша приёмка  → запускаете и проверяете вручную           → коммит
   └─ повторяете шаги 4–6 для следующей задачи
```

Больше всего времени стоит вложить в шаги 1–3. Ошибку в спецификации исправить легко, пока код не написан, а потом её приходится исправлять во многих местах.

## Как начать эксперимент

1. Создайте отдельную папку проекта и выполните `git init`. Без истории коммитов неудачную попытку агента трудно откатить.
2. Скопируйте содержимое этой папки в корень проекта. `CLAUDE.md` и `.claude/` должны лежать там, откуда вы запускаете агента.
3. Замените содержимое `docs/` на свой проект. Можно попросить агента провести интервью (см. [`PROMPTS.md`](PROMPTS.md)).
4. Выполняйте задачи из `BACKLOG.md` по одной, начиная с каркаса и проверок.

## Что проверять вам

Зелёные тесты не доказывают, что всё правильно: агент мог написать тесты под свой код. Поэтому при приёмке смотрите:

- **Соответствие задаче.** Каждый критерий закрыт, лишних функций нет.
- **Тесты.** Они проверяют поведение из спецификации. Существующие тесты не удалены и не ослаблены, чтобы пройти проверку.
- **Работа вживую.** Запустите приложение и пройдите основной сценарий: тесты могут не заметить проблему запуска или настройки.
- **Безопасность.** Посмотрите на доступ к данным, проверку прав, секреты и новые зависимости.
- **Размер diff.** Изменения должны быть понятны вам. Если это не так, просите агента объяснить их или разбить задачу на части.

## Частые ошибки

- **Большая задача одним запросом** («сделай весь проект»). Результат невозможно нормально проверить.
- **Размытые критерии** («должно работать быстро и удобно»). Лучше написать то, что можно проверить: «ответ 404 с кодом `quiz_not_found`».
- **Одна сессия на весь проект.** Контекст засоряется, и качество падает. Для новой задачи начинайте новую сессию, а всё важное храните в файлах.
- **Исправления только в чате.** Если поведение изменилось, сначала обновите спецификацию, иначе следующая сессия об этом не узнает.
- **Ревью в той же сессии, где писался код.** Агент склонен защищать свои решения. Новая сессия смотрит на код свежим взглядом.
