# Кэширование в Redis

Дополняет `docs/SPEC.md` (решение 6 в `docs/decisions.md`). Цель: материалы (вопросы, тесты, справочники, библиотека, снимки игры) читаются из Redis, а PostgreSQL обрабатывает в основном записи и промахи кэша.

## Принципы

1. **PostgreSQL остаётся источником истины.** Redis хранит только копии, которые можно восстановить. Если очистить Redis целиком (`FLUSHALL`), система продолжает работать правильно, только медленнее. Отдельный тест это проверяет.
2. **Cache-aside.** Чтение идёт сначала в Redis, при промахе в базу, затем результат записывается в Redis. Запись идёт в базу, после коммита кэш инвалидируется.
3. **Инвалидация после коммита,** в том же хуке, что и публикация в Centrifugo. Если транзакция откатилась, кэш не трогается.
4. **Удаление ключа, а не перезапись.** Это исключает гонку двух писателей, при которой в кэше остаётся старое значение.
5. **TTL на каждом ключе.** Это страховка от пропущенной инвалидации: устаревшие данные проживут не дольше TTL.
6. **Публичное и приватное в разных ключах.** Варианты с правильными ответами (`QuestionWithAnswers`) и публичные варианты (`QuestionPublic`) никогда не хранятся в одном значении. В публичный ключ сериализуется только публичная схема.
7. **Недоступность Redis не ломает запросы.** При ошибке Redis запрос читает базу и пишет предупреждение в лог. Исключение составляет rate limit, см. ниже.
8. **Защита от наплыва при промахе.** Значение пересчитывает один запрос, взявший короткую блокировку `SET lock:<key> NX PX 3000`. Остальные ждут до 200 мс и читают кэш, а по таймауту идут в базу.

## Что кэшируется

| Данные | Ключ | Значение | TTL | Когда сбрасывается |
|---|---|---|---|---|
| Вопрос (для автора) | `q:{id}:full` | `QuestionWithAnswers` | 1 ч | изменение или удаление вопроса, публикация, снятие с публикации |
| Вопрос (публичный) | `q:{id}:public` | `QuestionPublic` | 1 ч | то же |
| Тест с порядком вопросов | `quiz:{id}` | настройки и упорядоченный список `question_id` | 1 ч | изменение теста, `PUT /questions`, удаление |
| Мои вопросы и тесты | `user:{uid}:questions:v{n}:{hash(фильтры)}`, `user:{uid}:quizzes` | список id и полей карточек | 10 мин | любое изменение своих вопросов или тестов: `INCR user:{uid}:questions:ver` |
| Категории | `categories:all` | все категории | 24 ч | создание категории |
| Автодополнение | `cat:ac:{prefix}`, `tag:ac:{prefix}` | до 10 элементов | 10 мин | только TTL |
| Страницы библиотеки | `lib:v{n}:{hash(фильтры, cursor)}` | список id и курсор | 5 мин | публикация, снятие, изменение или удаление публичного вопроса: `INCR lib:ver` |
| Снимок комнаты | `room:{id}:state` | ответ `GET /rooms/{id}` без личной части | до конца игры + 1 ч | каждый переход статуса, join, leave, ready, kick |
| Раунд (проверка) | `round:{id}:check` | `question_snapshot` с правильными ответами и `deadline_at` | до `ended_at` + 10 мин | неизменяем. Удаляется после завершения игры |
| Итоги | `room:{id}:results` | ответ `/results` | 24 ч | неизменяемы после `finished` |
| Профиль | `user:{uid}:profile` | `/users/me` | 30 мин | изменение профиля |

Списки хранят только id, а карточки берутся из ключей сущностей через `MGET`. Это позволяет инвалидировать одну сущность, не трогая все страницы, где она встречается.

Версия в ключе списка (`lib:ver`, `user:{uid}:questions:ver`): при изменении версия увеличивается, и старые страницы перестают читаться. Они удаляются сами по TTL, поэтому `SCAN` и удаление по маске не нужны.

## Что не кэшируется

- **Приём ответа и закрытие раунда.** Эти операции остаются транзакциями PostgreSQL с `FOR UPDATE` и `UNIQUE` (раздел 8 ТЗ). Redis используется только для чтения снимка вопроса при проверке ответа (`round:{id}:check`), чтобы не читать `room_rounds` на каждый ответ.
- **Refresh-токены и права доступа.** Проверка прав выполняется на актуальных данных. Права из кэша можно использовать только вместе с проверкой в базе на мутирующих запросах.
- **Таймеры раундов.** Воркер работает по базе (`SKIP LOCKED`), как в ТЗ.

## Другие задачи Redis

- **Хранилище rate limit** (slowapi, `storage_uri=redis://...`). Если Redis недоступен, лимиты на вход и регистрацию запрещают запрос (fail closed). Остальные лимиты пропускают запрос и пишут ошибку в лог.
- Centrifugo остаётся с брокером в памяти, как в MVP по ТЗ. Тот же Redis можно подключить брокером позже, при нескольких экземплярах Centrifugo.

## Реализация

- Сервис `redis` (`redis:8` или актуальная стабильная версия, проверить по описанию образа) в `docker-compose.yml`, `appendonly no`, `maxmemory 256mb`, `maxmemory-policy allkeys-lru`. Переменная `REDIS_URL=redis://redis:6379/0` в `.env.example`.
- Модуль `app/core/cache.py`:
  - клиент `redis.asyncio`;
  - обёртка `get_or_load(key, ttl, loader, schema)`, которая сериализует Pydantic-схему в JSON и защищает от наплыва;
  - `invalidate(*keys)` и `bump(version_key)`, которые вызываются после коммита.
- Ключи формируются только функциями из `app/core/cache_keys.py`. Строки ключей вручную не собираются.
- Сервисы вызывают кэш, а репозитории о нём не знают.
- Метрики попаданий и промахов пишутся в structlog. Prometheus подключается опционально.
- `/readyz` проверяет Redis. Недоступность Redis переводит статус в `degraded` с кодом 200, потому что сервис продолжает работать (принцип 7).

## Тесты (TDD)

Каждая кэшируемая сущность должна иметь тесты:

1. Второе чтение не обращается к базе. Счётчик запросов SQLAlchemy через event listener не растёт.
2. После изменения следующее чтение возвращает новые данные. Проверяются все пути инвалидации из таблицы выше.
3. Если транзакция откатилась, кэш не изменился.
4. В публичных ключах нет полей правильности. Рекурсивная проверка выполняется по содержимому Redis, а не только по HTTP-ответу.
5. После `FLUSHALL` ответы идентичны.
6. При недоступном Redis (клиент подменён на падающий) запросы чтения работают, а вход и регистрация отвечают 503.

В тестах используется отдельная база Redis (`/15`), которая очищается перед каждым тестом.
