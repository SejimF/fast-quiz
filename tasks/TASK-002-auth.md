# TASK-002: Аутентификация

## Зачем

Пользователь получает учётную запись, а остальные модули могут опираться на текущего пользователя.

## Контекст

`docs/SPEC.md`: раздел 3 (`users`, `refresh_tokens`), раздел 4 (модули `auth` и `users`, эндпоинты `/auth/*`, `/users/me`, формат ошибок), раздел 8 («Безопасность»), раздел 7 (страницы `/login` и `/register`).

## Что сделать

- Миграция для `users` и `refresh_tokens` с расширением `citext`.
- Бэкенд: `register`, `login`, `refresh` с ротацией, `logout`, `GET /users/me`, зависимость `current_user`. Пароли хешируются argon2id. Access-токен PyJWT живёт 15 минут, refresh-токен 30 дней и хранится в cookie `httpOnly; Secure; SameSite=Lax`, а в базе лежит только его хеш.
- Единый формат ошибок из раздела 4 для всех ответов, включая 422.
- Фронт: страницы входа и регистрации на React Hook Form и Zod, ошибки бэкенда в полях, access-токен в памяти, автоматический refresh, защита маршрутов, выход.

## Критерии приёмки

- [ ] **AC1.** Регистрация с валидными данными возвращает пользователя и токены. `username` занимает 3–32 символа из `[a-z0-9_]`, пароль не короче 8 символов.
- [ ] **AC2.** Занятые `email` или `username`, без учёта регистра, дают `409` или `422` с указанием поля. Выбранный код нужно записать в `docs/decisions.md`.
- [ ] **AC3.** Вход работает по `email` или по `username`. Неверный пароль даёт `UNAUTHORIZED` и не сообщает, какое поле неверно.
- [ ] **AC4.** `refresh` выдаёт новую пару токенов и отзывает старый refresh. Повторное использование старого refresh-токена даёт 401.
- [ ] **AC5.** После `logout` refresh-токен не работает.
- [ ] **AC6.** `GET /users/me` без токена или с просроченным токеном даёт `UNAUTHORIZED`.
- [ ] **AC7.** Пароль и его хеш не попадают ни в один ответ и ни в логи.
- [ ] **AC9.** Если Redis недоступен, вход и регистрация отвечают 503: rate limit работает по принципу fail closed (`docs/cache.md`). Сам лимит проверяется в TASK-010.
- [ ] **AC10.** `/users/me` кэшируется в `user:{uid}:profile`. Refresh-токены в кэш не попадают.
- [ ] **AC8.** Фронт: пользователь регистрируется, входит, остаётся в системе после перезагрузки страницы благодаря refresh, выходит. Защищённый маршрут без сессии перенаправляет на `/login`.

## Тесты в порядке написания (TDD)

1. `unit`: хеширование и проверка пароля, выпуск и проверка access-токена с подменёнными часами (истёк или нет).
2. `integration`: регистрация, валидация полей, дубли.
3. `integration`: вход и ошибка неверного пароля.
4. `integration`: ротация refresh-токена, повторное использование, logout.
5. `integration`: `/users/me` и доступ без токена.
6. `vitest`: форма показывает ошибки бэкенда в полях, guard перенаправляет на `/login`.

## Граничные случаи

- `Email` и `email` с другим регистром считаются одним адресом (`citext`).
- Два одновременных `refresh` с одним токеном: срабатывает только один.

## Вне области этапа

- Rate limit (TASK-010), поиск пользователей (TASK-007), восстановление пароля.

## Как проверить вручную

Зарегистрироваться на `localhost:5173/register`, перезагрузить страницу, выйти. В DevTools проверить, что у refresh-cookie стоят флаги `HttpOnly` и `SameSite=Lax`.
